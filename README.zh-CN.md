# 安装

1. 通过上方链接下载 `Metamorph-Creative-Menu.zip`。
2. 启动 Noita，在主菜单中打开 **Mods**。
3. 点击 **Open mods folder**。
4. 将 `metamorph_creative_menu` 文件夹解压或移动到 `mods` 目录。最终路径应直接包含 `metamorph_creative_menu/mod.xml`，不能多套一层压缩包目录。
5. 如果已经安装旧版本，请直接替换整个 `metamorph_creative_menu` 文件夹，不要把新旧文件合并。
6. 回到 Noita 并刷新模组列表。
7. 允许 **Unsafe Mods**。
8. 启用 **Metamorph: Creative Menu**，然后使用已启用模组开始游戏。

不要同时启用 GitHub standalone 构建和 Steam Workshop 构建。

# Standalone 构建与 Steam Workshop

本 GitHub 仓库提供的是完整 standalone 构建。它包含 NoitaPatcher，以及需要不受限 mod API 访问的功能，包括低层材料操作和原生 Game Over 恢复。

[Steam Workshop 构建](https://steamcommunity.com/sharedfiles/filedetails/?id=3785170245)独立安装，不包含 standalone 专属功能所需的原生组件。

两种构建使用相同的模组身份。同时安装可能造成文件重复或冲突，因此不受支持。

# 模组简介

**Metamorph: Creative Menu (MCM)** 是 Noita 的创造模式菜单和沙盒工具集。

它把以下工具集中到同一套界面中：

- 法术和法术背包；
- 法杖编辑与可重复使用的法杖预设；
- 物品和液体容器；
- 完整材料目录与材料绘制；
- 天赋以及受支持的天赋移除；
- 状态效果与 GameEffect 实体；
- 生物、变形与附身；
- 天气与时间；
- 全局世界规则；
- 传送；
- 可选的 Entangled Worlds 集成；
- 变形、形态死亡和 Game Over 后的恢复路径。

MCM 尽量直接操作 Noita 的真实状态，而不是用装饰性的复制品代替一切。已有法术卡会尽可能作为真实实体移动；物品投递会尊重背包结构；法杖修改使用 commit/rollback 路径；材料保持为真实参与模拟的材料；可逆世界规则会保留足够的原始状态，以便之后恢复受支持的设置。

Entangled Worlds 是可选的。没有它时，MCM 仍然是完整的单人模组。

# 操作

默认按键：

| 操作 | 默认输入 |
| --- | --- |
| 打开 / 关闭创造菜单 | **F4** |
| 变形期间返回人类形态 | **TAB** |
| 附身到世界中的生物 | **G** |
| 用选中的材料绘制 | **鼠标中键** |

创造面板也可以通过 Noita 的普通背包界面访问。

按键可在 MCM 的 **CONTROLS** 页面和 Noita 模组设置中修改。支持键盘按键、鼠标按键，以及精确的 **CTRL / SHIFT / ALT** 组合。

捕获按键时：

- **DELETE / BACKSPACE** 清除绑定；
- **ESC** 取消；
- **R** 恢复该操作的默认绑定；
- **RESET ALL** 在确认后恢复全部默认绑定。

重复绑定仍然可以保留，但 MCM 会显示冲突，而不是静默覆盖另一个操作。

菜单导航、各页面、返回人类形态、附身、材料绘制、效果清理、释放天气控制、重置世界规则以及受支持的多人操作都可以重新绑定。

# Creative Menu 窗口

独立创造面板是可持久保存、可缩放的窗口，不是固定 debug overlay。

窗口可以：

- 通过标题栏拖动；
- 从边缘和角落缩放；
- 最小化；
- 关闭；
- 恢复默认布局。

位置、宽度、高度和上次打开的页面会在多次启动之间保存。分辨率改变后，保存的窗口几何会重新限制到可见 GUI 范围内。

列表和目录使用经过测量的布局和 Noita 滚动容器。调整窗口大小会立刻改变可见内容数量，翻译后的长文本可以正常换行而不覆盖相邻控件。在狭窄布局中，控件会换到新行，而不是互相叠在一起。

单纯打开或悬停在独立窗口上不会永久禁用游戏控制。当点击、拖动或正在编辑的文本框可能同时触发玩家操作时，MCM 会暂时抑制相关玩家输入，并在之后恢复。

# 搜索与本地化

主要目录都支持搜索，包括法术、物品、材料、天赋和生物。

根据条目类型，搜索可以匹配：

- 当前界面语言名称；
- 英文名称；
- 本地化 key；
- 技术标识符；
- XML 路径。

搜索不区分大小写，会规范化常见重音与分隔符，并对较长查询中的小型拼写错误具有一定容错。

MCM 自有界面支持：

- 英语；
- 俄语；
- 巴西葡萄牙语；
- 西班牙语；
- 德语；
- 法语；
- 意大利语；
- 波兰语；
- 简体中文；
- 日语；
- 韩语。

对于普通 Noita 内容，模组会尽量复用游戏本身的本地化 key，而不是维护重复名称。

# 法术

法术页面既能操作目录，也能操作玩家已经拥有的真实法术实体。

主工作区包含：

- 当前法杖的普通槽位；
- **ALWAYS CAST** 卡；
- 玩家法术背包；
- 可搜索的法术目录。

## 快速替换选中槽位

短按一个法杖槽位会选中它。随后短按目录中的法术即可替换选中的槽位。

这是普通编辑的快速方式。精确移动使用 drag-and-drop。

## 事务式 drag-and-drop

已有法术卡可以拖动：

- 在法杖槽位之间移动；
- 从普通槽位移入 **ALWAYS CAST**；
- 从 **ALWAYS CAST** 移回普通槽位；
- 放入法术背包的指定槽位；
- 从背包放回法杖；
- 丢到游戏世界；
- 在受支持时放入垃圾桶。

对于已有卡牌，MCM 会尽量移动真实实体。因此可变状态、剩余使用次数以及其他模组添加的数据不会仅因为换位置就被丢失。

在目标事务确认之前，来源保持不变。无效或未知的目标会取消操作，而不是删除原卡。一次鼠标释放最多提交一项操作。

目录卡片只是模板，拖动不会消耗它们。

## Always Cast

Always Cast 有独立区域。把卡牌提升、移回或交换时，会考虑普通槽位的有效容量，以避免形成无效法杖结构。

## 撤销与重做

法杖内部修改拥有有限的 **UNDO / REDO** 历史。

如果操作把真实实体交给外部世界或其他背包，仅依靠法杖 snapshot 并不总能安全回收它，因此这些外部 handoff 不承诺永远可撤销。

# 法杖

法杖工作区编辑玩家当前手持的法杖。

支持的属性包括：

- 容量 / 槽位；
- 每次施放的法术数；
- 充能时间；
- 施法延迟；
- 散射；
- 投射物速度倍率；
- 最大法力；
- 法力回复速度；
- 后坐恢复；
- 法杖等级；
- shuffle；
- 无需充能行为。

MCM 也可以编辑外观与相关元数据：

- 显示名称；
- 法杖和卡牌锁定；
- sprite 路径；
- sprite 偏移；
- 发射位置。

有数据可用时，视觉外观目录会遵循法杖 XML 中定义的内容。

## 法杖预设

法杖可以保存为持久命名预设，并在之后的世界或 Noita 会话中再次使用。

预设可保存：

- 法杖属性；
- 法力值；
- 视觉元数据；
- 普通法术卡；
- Always Cast 卡；
- 槽位位置；
- 剩余使用次数；
- 卡牌冻结状态。

每个预设有两个独立操作：

- **APPLY** 把保存的 blueprint 应用到当前手持法杖；
- **GET COPY** 根据同一 blueprint 创建一根新法杖。

如果快速背包有空闲法杖槽位，新法杖会放入那里。若没有合适槽位，完整构建的法杖会留在玩家附近的世界中。

法杖替换和预设加载使用 commit/rollback 路径。如果构建或放置无法完成，MCM 会尝试移除不完整实体树，而不是留下损坏的半成品法杖。

# 物品与液体

## 物品

短按目录条目的 **LMB** 会在玩家附近创建一个受支持的物品。

**RMB** 会尝试把物品交给合适的背包区域。

目录条目也可以拖动：

- 放到匹配的快速背包目标；
- 拖出菜单到世界中的精确位置。

如果在菜单内部没有有效目标时松开卡片，操作会取消。目录卡片只是模板，会继续保留。

MCM 尊重 Noita 快速背包中法杖槽位和物品槽位的正常区分。如果 XML 加载、液体填充、背包投递或可选多人 handoff 失败，新创建的实体会在可能时被清除。

一些真正的背包物品存放在游戏中偏向生物的目录下。MCM 会根据已知行为分类，而不是仅凭目录名判断它究竟是物品还是生物。

## 液体

液体条目会创建真实、已填充的 Noita 容器，而不是装饰性 UI 对象。

容器可以携带、丢弃、打碎并倒出内容，其内容会参与正常的材料反应。

# 材料

Materials 页面是基于 Noita 真实材料注册表的世界绘制工具。

目录来自 engine 注册的液体、沙 / 粉末、气体、火焰、固体以及相关静态或效果材料。其他已启用模组正确注册的材料也可以自动出现。

材料发现和高开销验证会拆分为受限工作，而不是在一个 UI 帧内扫描整个目录。

## 材料显示

液体使用与物品页相同的已填充容器显示方式。

对于非液体材料，MCM 优先使用 `materials.xml` 中定义的纹理和 tint，包括继承定义。如果没有定义纹理，则 fallback 来自 engine 中材料的真实颜色，而不是任意预览色。

## 绘制

1. 选择材料。
2. 选择画笔大小。
3. 开启绘制模式。
4. 关闭背包。
5. 在世界中按住已配置的绘制输入。

重新打开背包会停止当前绘制模式。

绘制并不是简单发射装饰粒子。MCM 会通过适合 engine 的路径把真实 cell 写入世界。动态材料继续遵循 Noita 模拟：液体流动、粉末下落、气体移动、火焰反应，不稳定物质也能通过材料反应继续变化。

不同材料类别需要不同放置策略。Standalone 构建可以使用 NoitaPatcher 的直接世界网格访问，并在 Noita 无法直接在特定纹理坐标构造已定义材料时使用小型 PixelScene fallback。

工作队列有上限，因此长时间使用大画笔不会故意在单帧内执行无限工作。

# 天赋

## 创建与获取天赋

**LMB** 会在世界中创建选中天赋的普通 pickup。

获取操作可以单次或批量授予天赋。批量操作通过有上限的 job 分帧处理，而不是在一个 UI 帧中应用所有副本。

界面会显示进度，尚未执行的工作可以取消。取消前已经提交的副本会继续保留。

每一份授予仍会走正常的天赋应用路径，而不是直接伪造最终状态。

## 移除天赋

移除天赋远比授予复杂。天赋可能修改 globals、组件、实体、玩家属性和长期机制，而 Noita 并不存在一个通用逆操作。

因此 MCM 只移除那些拥有足够安全、可追踪逆操作的状态。事务 journal 会尝试只删除属于该次天赋应用的状态，而不重置无关玩家状态。

如果清理只完成了一部分，或者无法证明已经完全清理，它会继续被视为未完成，而不是静默报告成功。

第三方天赋可能可以授予，但不一定能被正确移除。

# 效果

Effects 页面可以应用和移除受支持的材料状态以及 GameEffect 实体。

移除时会在可能的情况下考虑状态所有权。MCM 不会无差别删除看似相似但属于天赋、游戏本身或其他系统的隐藏效果。

由 MCM 创建的持久效果使用受限清理 / 到期处理，以避免删除一个 MCM 效果时重置无关状态。

# 生物

生物目录保留精确 XML 路径，不会把所有名字相似的实体合并为同一个条目。

支持的操作：

- **LMB** — 在玩家附近创建选中的定义实体；
- 拖出菜单 — 在确认的世界光标位置创建；
- **RMB** — 把当前玩家变形成受支持形态；
- 特殊 **PLAYER** 条目 — 按下文说明创建或恢复玩家相关状态。

把拖动中的生物卡放回菜单上会取消世界 spawn。

危险或特殊形态的兼容规则基于精确路径。文件名里只是包含一个熟悉词语，并不会让该实体自动被当成另一种等价形态。

# 变形与返回人类形态

可玩形态会尽量保留有用的原生移动、攻击、外观和物理行为。与玩家输入直接冲突的组件，在玩家控制该形态期间可能会被禁用或适配。

部分复杂生物需要额外兼容逻辑。Boss、脚本 wrapper 和强依赖物理的实体在作为玩家形态时，不保证与其 AI 控制的原始版本完全一致。

已配置的返回操作——默认 **TAB**——会先尝试正常结束变形。如果不够，standalone 构建还提供 NoitaPatcher 支持的额外恢复路径。

在受支持的致死伤害情况下，MCM 会尝试：

- 在合适时让死亡的临时形态或尸体留在世界中；
- 恢复人类玩家实体；
- 归还 authority 和控制权；
- 保留背包；
- 恢复相关玩家状态。

这是恢复逻辑，不是绝对不死。第三方 kill script、不兼容的 engine 状态或进程崩溃可能绕过受支持的 handoff。

# 附身

附身会控制已经存在于世界中的生物，而不是从目录里选择一种形态。

默认按键是 **G**。

指向合适的生物并使用附身操作。MCM 会检查目标、准备兼容的形态切换，并且只在新的玩家控制状态确认成功后，才移除或 retirement 原始世界实体。

如果切换失败，原始生物不应直接消失。

附身不限于 MCM 内置目录。其他模组创建的兼容生物也可能工作，但不保证兼容所有第三方实体。

# Player 条目

**PLAYER** 是生物目录中的特殊条目，不是普通 polymorph 目标。

它的 spawn 操作会创建独立的类玩家角色，并尝试复制适合的玩家外观和最大生命信息。

对 **PLAYER** 使用变形操作不会把已经是人类的玩家变成复制体。如果玩家当前处于其他形态，该操作会作为返回人类形态使用。

# 单人 Game Over 恢复

Standalone 单人构建为 Noita 原生 Game Over 画面提供额外恢复路径。

当原生集成能够安全识别所需的游戏结构时，MCM 会在 Game Over 界面加入 **“I didn't die”** 操作。

游戏运行期间，MCM 会持续维护玩家状态备份。触发恢复后，会通过 MCM 的正常更新路径请求恢复，而不是直接在 UI 点击 handler 中重建完整玩家。

受支持的恢复会尝试：

- 恢复或取得存活玩家实体；
- 重新让它成为 authoritative；
- 清除 engine 的 Game Over 状态；
- 恢复控制和可用的玩家状态；
- 尽力清理 Game Over 音频、音乐和 UI 状态；
- 在恢复后提供短暂保护窗口。

原生 helper 采用 fail-closed 设计。它会扫描正在运行、受支持的 Noita executable 中的已知结构，而不是永久写死一个地址。如果游戏更新后无法安全识别预期结构，可选恢复功能就不会启用，而不是向不确定地址写入。

# 天气与时间

MCM 可以控制受支持的天气和时间状态，包括预设以及当前实现暴露的单独参数。

强制状态之后可以释放回游戏的正常控制。例如，强制某个时间点后，MCM 可以放弃对该设置的控制，让 Noita 自然时间再次运行。

天气修改被当作有状态控制，而不是一次性、不可逆的控制台命令。

# 世界规则

**RULES** 页面修改受支持的全局游戏行为。

规则覆盖例如：

- 生物关系；
- 金钱行为；
- 法术使用；
- fog of war；
- 某些击杀奖励；
- 治疗掉落；
- 与血液相关的行为；
- 重力；
- 物理行为；
- 踢击力量；
- 物理连接；
- 昼夜循环；
- 其他受支持的全局参数。

核心目标是可逆性。

对于受支持的规则，MCM 会记录或推导原始状态，以便之后恢复。倍率控制相对于原始值计算，而不是不断对已经修改过的结果继续乘算。

需要处理大量实体或物理对象的规则会使用分帧、受限工作，而不是一次菜单点击就同步重写整个世界。

# 传送

传送页面提供预设世界目标，包括主路线、Holy Mountains、主要支线区域以及其他受支持地点。

移动玩家前，MCM 可以请求加载目标区域，并寻找附近可用的空闲空间，而不是故意把玩家直接放进固体地形。

传送仍依赖世界本身能够加载并提供有效目标。高度修改的世界可能需要 fallback 行为。

# Entangled Worlds

**Entangled Worlds / Noita Proxy 是可选的。** 没有 EW 时 MCM 也能工作。

当 EW 存在时，MCM 会启用额外的多人感知行为。依赖 MCM 特定同步状态时，所有 peer 都应使用兼容的 MCM 构建。

## Authority 与形态

玩家形态需要特殊 ownership 处理，因为变形后的玩家不应该意外留下第二个网络 authority。

在受支持的情况下，MCM 会与 EW 协调形态 ownership、retirement 以及返回人类形态。Boss 和 Kolmi 类实体还有额外 lifecycle 处理，用于避免重复 authority 和陈旧的网络控制副本。

对于未识别为 MCM-owned 形态状态的实体，EW 的普通死亡路径仍然负责处理。

## 物品、法杖与法术

只要可行，MCM 会使用 EW 正常的 item / inventory 机制，而不是发明平行的传输系统。

已提交的法杖和法术背包修改会在集成可用时请求对应的多人 refresh。MCM 创建的世界物品可以交给 EW 标准 world-item 路径。

## 天赋

普通天赋 pickup 可以使用 EW 的标准 world-item 同步。MCM 自己的天赋状态处理会协调 refresh 和受限操作，避免批量行为为每个副本都触发一次昂贵的全局刷新。

## 材料

材料绘制有专门兼容路径，因为世界 cell 修改不是普通 item entity。

MCM 会限制绘制工作，在 chunk 边界拆分任务，并在释放同步转换工作前协调 EW 需要的 world-frame / persistence 步骤。尚未加载的 streaming 边缘 chunk 会被延后，而不是阻塞整条当前笔画。

目标是让附近 EW peer 能看到受支持的绘制世界状态，而不需要把普通 MCM UI 操作远程重放成只基于 filename 的 PixelScene 调用。

这仍然继承 EW 对 material id 的假设：接收端游戏无法正确创建自己不存在的材料，也无法处理不兼容的 engine 材料注册表。

## 天气、附身与世界状态

受支持的 MCM 多人状态还包括天气、附身以及部分世界规则 / lifecycle 行为的协调。Authority 检查可以避免两个 peer 同时试图拥有同一状态。

EW 支持刻意保持保守。如果集成无法证明安全同步路径，MCM 宁可保留正确的本地行为，也不会假装每个单人操作都自动适用于多人。

# 兼容性与限制

Noita 通过松散耦合的实体、XML、Lua 组件和原生 engine 行为提供许多系统。因此 MCM 无法保证与所有修改实体或未来所有游戏更新完全兼容。

重要限制包括：

- 能 spawn 的生物不代表它一定是安全的玩家形态；
- 能授予的天赋不代表一定有可靠逆操作；
- 外部法术或物品 handoff 不一定能从内部 snapshot 撤销；
- 第三方脚本可能绕过受支持的死亡与恢复路径；
- 原生恢复依赖受支持的 Noita executable 行为，如果无法识别所需结构则会 fail-closed；
- Entangled Worlds 无法同步接收端注册表中不存在的材料；
- 高度修改的背包、实体或世界规则可能需要针对特定模组的兼容处理。

MCM 会尽量保留原始状态并回滚失败修改，但一个直接修改实时游戏状态的沙盒工具无法让所有第三方模组组合都变成完全事务式。

# 保存数据

MCM 会保存应该跨多次运行保留的用户状态，包括受支持设置、按键绑定、菜单布局和法杖预设。

模组身份保持稳定，因此正常升级可以继续使用受支持的保存数据。安装新的 standalone 构建时仍建议整体替换模组文件夹，因为混合旧文件和新文件可能留下过时 runtime。

# 故障排除

## 模组没有出现

确认目录最终为：

`mods/metamorph_creative_menu/mod.xml`

如果 `metamorph_creative_menu` 上面多出一层压缩包目录，Noita 无法正确识别模组。

## 原生功能或材料功能不工作

确认已经允许 **Unsafe Mods**，并且安装的是 GitHub standalone 构建，没有与 Workshop 文件混装。

## 菜单打开时也触发了游戏操作

检查自定义绑定是否冲突。MCM 会显示重复绑定，但如果你需要，也允许保留它们。

## 某个生物无法安全变形

并不是所有可 spawn 的 XML 实体都是受支持玩家形态。需要特殊处理的生物会使用精确路径兼容规则。

## 某个天赋无法移除

只有当 MCM 对已追踪状态拥有受支持逆操作时才提供移除。这是有意限制；猜测式清理可能破坏无关玩家状态。

## 多人环境中不同 peer 行为不一致

所有参与者都应使用兼容的 MCM 构建，并保持兼容的 Noita / Entangled Worlds 环境。MCM 无法修复不兼容的材料注册表或其他模组任意的网络修改。

# 报告问题

有用的问题报告应包括：

- 你原本想做什么；
- 涉及的 MCM 精确页面和操作；
- 问题出现在单人、Entangled Worlds，还是两者都有；
- 安装的是 standalone 还是 Workshop 构建；
- 是否启用了其他 gameplay 模组；
- 可稳定复现的步骤；
- 有条件时附上相关 Noita / EW 日志。

对于变形、附身、物品或材料问题，请尽量给出精确实体或材料。技术标识符通常比翻译后的显示名称更有帮助。

# 仓库与开发源码

仓库有意保留**完整开发源码树**，而不是玩家下载的同一份精简压缩包。

`metamorph_creative_menu/` 除 runtime 代码外还包含：

- 自动化测试；
- QA 工具；
- 诊断代码；
- 原生源码；
- 构建工具；
- release 清理规则；
- 开发文档。

这些内容对开发和回归测试有用，因此会保留在 GitHub source 中。面向玩家的 ZIP 会单独生成，并排除 development-only 内容。

玩家包还会执行仅 release 使用的清理，包括最小化的 player `README.txt`；source tree 则保留正常的开发文档。

# 测试

自动测试位于 `metamorph_creative_menu/tests/`，包含 Python contract 检查和 Lua mock 测试。

Release workflow 会从仓库根目录对完整导入 source 运行测试，通过后才发布 player build。Lua mock 部分需要 `texlua`。

Source hygiene 检查还会保护面向 production 的文件和文档，避免开发历史残留、过时 debug 接口以及意外流程产物重新进入仓库。

# Source 导入与发布流程

完整开发 source 可以从 `Metamorph-Creative-Menu-v...zip` 系列压缩包导入。

导入 workflow 会验证压缩包结构，要求完整开发组件，运行 source hygiene 和回归测试，然后才提交导入后的源码树。

ModWorkshop / player 风格压缩包不会被当作开发 source。

公开的 `latest-build` release 会再通过独立 player-builder 从完整 source 生成。它会删除 QA、测试、诊断、原生源码以及其他 development-only payload，应用 release cleanup 规则，验证最终压缩包，然后才更新稳定下载 asset。

这种分离让仓库继续保持完整开发能力，同时让普通玩家下载保持精简且不包含开发 instrumentation。

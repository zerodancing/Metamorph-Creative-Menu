GitHub の release は完全な開発ソースツリーから自動生成されます。テスト、QA ツール、診断、ネイティブソース、ビルドツールはリポジトリに残りますが、プレイヤー向けアーカイブには含まれません。

GitHub の standalone ビルドには NoitaPatcher とネイティブ復旧機能が含まれるため、**Unsafe Mods を許可**する必要があります。

# インストール

1. 上のリンクから `Metamorph-Creative-Menu.zip` をダウンロードします。
2. Noita を起動し、メインメニューから **Mods** を開きます。
3. **Open mods folder** を押します。
4. `metamorph_creative_menu` フォルダを `mods` に展開または移動します。最終的なパスは余分なフォルダを挟まず、直接 `metamorph_creative_menu/mod.xml` を含む必要があります。
5. 古いコピーがある場合は、新旧ファイルを混在させず `metamorph_creative_menu` フォルダ全体を置き換えてください。
6. Noita に戻り、Mod 一覧を更新します。
7. **Unsafe Mods** を許可します。
8. **Metamorph: Creative Menu** を有効にして、Mod 有効状態でゲームを開始します。

GitHub standalone ビルドと Steam Workshop ビルドを同時に有効にしないでください。

# Standalone ビルドと Steam Workshop

この GitHub リポジトリで配布されるものは完全な standalone ビルドです。NoitaPatcher と、制限のない mod API アクセスを必要とする機能を含みます。たとえば低レベル素材操作や、Game Over 後のネイティブ復旧です。

[Steam Workshop ビルド](https://steamcommunity.com/sharedfiles/filedetails/?id=3785170245) は別にインストールされます。Standalone 専用機能に必要なネイティブコンポーネントは含みません。

両方のビルドは同じ Mod ID を使います。同時インストールはファイルの重複や競合を起こす可能性があり、サポートされません。

# Mod について

**Metamorph: Creative Menu (MCM)** は Noita のクリエイティブメニュー兼サンドボックスツールキットです。

次の機能を 1 つの UI にまとめます。

- 呪文と呪文インベントリ
- 杖編集と再利用可能な杖プリセット
- アイテムと液体容器
- 完全な素材カタログと素材ペイント
- パークと、対応しているパークの解除
- ステータス効果と GameEffect エンティティ
- クリーチャー、変身、憑依
- 天候と時間
- グローバルなワールドルール
- テレポート
- 任意の Entangled Worlds 連携
- 変身、フォーム死亡、Game Over からの復旧経路

MCM は見た目だけのコピーで置き換えるのではなく、できる限り Noita の実際の状態を操作します。既存の呪文カードは可能な限り実体エンティティのまま移動し、アイテム受け渡しはインベントリ構造を尊重し、杖変更は commit/rollback を使い、素材は本物のシミュレーション対象として残り、可逆なワールドルールは復元に必要な元状態を保持します。

Entangled Worlds は必須ではありません。導入していなくても MCM は完全なシングルプレイ Mod として動作します。

# 操作

デフォルト操作:

| 操作 | デフォルト入力 |
| --- | --- |
| クリエイティブメニューを開く / 閉じる | **F4** |
| 変身中に人間へ戻る | **TAB** |
| ワールド内のクリーチャーに憑依 | **G** |
| 選択素材で描画 | **マウス中ボタン** |

クリエイティブパネルは Noita の通常インベントリ UI からも利用できます。

キー割り当ては MCM の **CONTROLS** セクションと Noita の Mod 設定から変更できます。キーボード、マウスボタン、正確な **CTRL / SHIFT / ALT** 組み合わせをサポートします。

キー設定中:

- **DELETE / BACKSPACE** — 割り当てを削除
- **ESC** — キャンセル
- **R** — その操作のデフォルトに戻す
- **RESET ALL** — 確認後、すべてのデフォルト割り当てを復元

同じキーを複数操作に割り当てること自体は可能ですが、MCM は別操作を黙って上書きせず競合を表示します。

メニュー移動、各セクション、フォーム解除、憑依、素材描画、効果クリーンアップ、天候の制御解除、ワールドルール初期化、対応マルチプレイ操作などは再割り当てできます。

# Creative Menu ウィンドウ

直接開くクリエイティブパネルは、固定の debug overlay ではなく、状態を保存するリサイズ可能なウィンドウです。

次の操作ができます。

- タイトル部分をドラッグして移動
- 辺や角からリサイズ
- 最小化
- 閉じる
- デフォルトレイアウトへ戻す

位置、幅、高さ、最後に開いていたセクションはセッション間で保存されます。解像度変更後は、保存された座標が見える GUI 領域内に収まるよう補正されます。

リストやカタログは測定済みレイアウトと Noita のスクロールコンテナを使います。ウィンドウサイズを変えると表示量も即座に変わり、長い翻訳ラベルは隣の UI に重ならず折り返されます。狭い幅ではコントロールが次の行へ回り、重なりません。

ウィンドウを開いたりカーソルを置いただけでゲーム操作が恒久的に無効になることはありません。クリック、ドラッグ、入力中のテキスト欄がプレイヤー操作と競合する場面だけ、MCM が関連操作を一時的に抑制し、その後復元します。

# 検索とローカライズ

呪文、アイテム、素材、パーク、クリーチャーなど主要カタログで検索できます。

項目によっては次の情報を検索対象にします。

- 現在の UI 言語での名前
- 英語名
- ローカライズキー
- 技術 ID
- XML パス

検索は大文字小文字を区別せず、一般的なアクセントや区切りを正規化し、長い検索語では軽いタイプミスも許容します。

MCM 自身の UI は次の言語に対応します。

- 英語
- ロシア語
- ブラジルポルトガル語
- スペイン語
- ドイツ語
- フランス語
- イタリア語
- ポーランド語
- 簡体中国語
- 日本語
- 韓国語

通常の Noita コンテンツについては、可能な限りゲーム本体のローカライズキーを再利用し、名前の重複管理を避けます。

# 呪文

呪文セクションはカタログだけでなく、プレイヤーが実際に持っている呪文エンティティも扱います。

メイン領域には次が表示されます。

- 現在の杖の通常スロット
- **ALWAYS CAST** カード
- プレイヤーの呪文インベントリ
- 検索可能な呪文カタログ

## 選択スロットのクイック置換

杖スロットを短くクリックすると選択状態になります。その後カタログの呪文を短く LMB クリックすると、そのスロットを置き換えます。

これは通常編集向けの高速操作です。正確な移動には drag-and-drop を使います。

## トランザクション式 drag-and-drop

既存カードは次の間で移動できます。

- 杖スロット間
- 通常スロットから **ALWAYS CAST**
- **ALWAYS CAST** から通常スロット
- 呪文インベントリの特定スロット
- インベントリから杖
- ゲームワールド
- 対応している場合はゴミ箱

既存カードは可能な限り実際のエンティティそのものを移動します。そのため可変状態、残り使用回数、他 Mod が追加した状態を単なる位置変更で失いにくくなっています。

移動元は、移動先のトランザクションが確定するまで保持されます。不正または未知のドロップ先では削除せずキャンセルします。1 回のマウスリリースで確定する処理は最大 1 件です。

カタログカードはテンプレートであり、ドラッグで消費されません。

## Always Cast

Always Cast には専用列があります。通常スロットとの昇格、降格、交換では通常スロットの実効容量を考慮し、不正な杖構造を作らないようにします。

## Undo / Redo

杖内部の変更には有限の **UNDO / REDO** 履歴があります。

実体エンティティをワールドや別インベントリに渡した処理は、杖の snapshot だけから安全に回収できるとは限りません。そのため外部 handoff は常に取り消せる機能としては扱いません。

# 杖

杖ワークスペースでは、現在手に持っている杖を編集します。

対応パラメータ:

- 容量 / スロット数
- 1 回の詠唱で使う呪文数
- リチャージ時間
- 詠唱遅延
- 拡散
- 投射物速度倍率
- 最大マナ
- マナ回復速度
- 反動回復
- 杖レベル
- shuffle
- no-reload 動作

外観や関連メタデータも編集できます。

- 表示名
- 杖 / カードのロック
- sprite パス
- sprite オフセット
- 発射位置

利用可能な場合、外観カタログは杖 XML に定義されたデータを利用します。

## 杖プリセット

杖は名前付きの永続プリセットとして保存でき、別ワールドや後の Noita セッションでも再利用できます。

プリセットに保存できるもの:

- 杖ステータス
- マナ値
- 見た目のメタデータ
- 通常呪文カード
- Always Cast カード
- スロット配置
- 残り使用回数
- カードの frozen 状態

各プリセットには 2 種類の処理があります。

- **APPLY** — 保存した blueprint を現在の杖に適用
- **GET COPY** — 同じ blueprint から新しい杖を作成

空いている杖用クイックスロットがあればコピーをそこへ入れます。適切なスロットがなければ、完成した杖をプレイヤー付近のワールドへ置きます。

杖置換とプリセット読み込みは commit/rollback を利用します。構築や配置が完了できない場合は、壊れた半完成杖を残す代わりに不完全なエンティティツリーを削除しようとします。

# アイテムと液体

## アイテム

カタログ項目を短く **LMB** クリックすると、対応アイテムをプレイヤー付近に 1 個生成します。

**RMB** は適切なインベントリ領域への格納を試みます。

カタログ項目を次の場所へドラッグすることもできます。

- 対応するクイックインベントリ領域
- メニュー外の正確なワールド位置

有効な対象がないままメニュー内で離すとキャンセルされます。カタログカードはテンプレートなので残ります。

MCM は Noita のクイックインベントリにおける杖とアイテムの区分を尊重します。XML 読み込み、液体充填、インベントリ受け渡し、任意の multiplayer handoff に失敗した場合、新規エンティティは可能な限り削除されます。

一部の実インベントリアイテムは、ゲーム上ではクリーチャー系ディレクトリに配置されています。MCM はフォルダ名だけで判断せず、既知のケースを挙動に基づいて分類します。

## 液体

液体項目は UI 上だけの表示物ではなく、実際に中身の入った Noita コンテナを生成します。

その容器は所持、投下、破壊、内容物の放出ができ、中身は通常の素材反応に参加します。

# 素材

Materials セクションは Noita の実際の素材レジストリを使うワールド描画ツールです。

カタログは engine に登録された液体、砂 / 粉末、ガス、火、固体、関連する静的素材やエフェクト素材から構成されます。他の有効 Mod が正しく登録した素材も自動的に現れることがあります。

素材探索や高コスト検証は 1 UI フレームですべて行わず、制限された処理量へ分散します。

## 素材表示

液体は Items セクションと同じ、内容入り容器の表示を使います。

非液体は `materials.xml` の定義済みテクスチャと tint を優先し、継承定義にも対応します。定義テクスチャがない場合のみ、任意のプレビュー色ではなく engine 上の実際の素材色を fallback に使います。

## ペイント

1. 素材を選びます。
2. ブラシサイズを選びます。
3. ペイントモードを有効化します。
4. インベントリを閉じます。
5. ワールドで設定済みの描画入力を押し続けます。

インベントリを開くとペイントモードは停止します。

ペイントは装飾粒子を出すだけではありません。MCM は engine に適した方法で実際のセルをワールドへ置きます。動的素材はその後も Noita のシミュレーションに従い、液体は流れ、粉末は落ち、ガスは移動し、火は反応し、不安定物質は素材反応で変化します。

素材クラスによって配置方法が異なります。Standalone ビルドは NoitaPatcher の直接ワールドグリッドアクセスを利用でき、Noita が特定のテクスチャ座標で直接構築を拒否する定義済みケースでは小型 PixelScene fallback を使います。

作業キューには上限があり、大きなブラシを押し続けても 1 フレームに無制限の処理を行う設計にはなっていません。

# パーク

## パークの生成と取得

**LMB** は選択中パークの通常 pickup をワールドに生成します。

取得操作は 1 個ずつでもまとめてでも実行できます。大量処理は 1 UI フレームですべて適用せず、上限付き job として分散処理されます。

UI は進行状況を表示し、未処理分はキャンセルできます。キャンセル前にすでに確定した分は残ります。

各コピーは最終状態を直接偽装するのではなく、通常のパーク取得経路を通ります。

## パークの削除

パークの削除は付与よりずっと複雑です。パークは globals、コンポーネント、エンティティ、プレイヤーステータス、長時間のゲームメカニクスを変更することがあり、Noita に万能な逆操作はありません。

そのため MCM は、十分安全に追跡できる逆処理を持つ状態だけを削除します。トランザクション journal は、そのパーク適用に所有される状態だけを消し、無関係なプレイヤー状態をリセットしないようにします。

クリーンアップが一部しか完了しない、または完全性を確認できない場合は、成功扱いにはせず未完了として残します。

第三者 Mod のパークは付与できても正しく削除できるとは限りません。

# 効果

Effects セクションでは、対応している素材ステータスと GameEffect エンティティを適用・削除します。

可能な場合は状態の所有元を考慮して削除します。MCM はパーク、ゲーム、別システムに属する類似の隠し効果を無差別に削除しません。

MCM が作成した永続効果は上限付きのクリーンアップ / 期限処理を使い、1 つの MCM 効果を消すだけで無関係な状態までリセットしないようにします。

# クリーチャー

クリーチャーカタログは正確な XML パスを保持し、名前が似ているだけのエンティティをまとめません。

対応操作:

- **LMB** — 選択中の定義済みエンティティをプレイヤー付近に生成
- メニュー外へドラッグ — 確定したワールドカーソル位置に生成
- **RMB** — 現在のプレイヤーを対応フォームへ変身
- 特殊 **PLAYER** 項目 — 下記のとおりプレイヤー関連状態を生成・復元

ドラッグしたカードをメニュー上へ戻して離すとワールド生成はキャンセルされます。

危険または特殊な変身対象の互換ルールは正確なパスで定義されます。ファイル名に似た単語が含まれるだけでは、別のフォームと同等とは扱いません。

# 変身と人間への復帰

プレイヤー用フォームは、実用的な範囲でネイティブの移動、攻撃、見た目、物理挙動を維持します。プレイヤー入力と直接競合するコンポーネントは、操作中だけ無効化または調整される場合があります。

複雑なクリーチャーには追加互換ロジックが必要です。Boss、スクリプト wrapper、物理依存の大きいエンティティは、プレイヤーフォーム時に元の AI 制御版と完全に同じ挙動を保証しません。

復帰操作——デフォルト **TAB**——はまず通常の変身終了処理を使います。それだけで足りない場合、standalone ビルドでは NoitaPatcher を使う追加復旧経路があります。

対応している致死ダメージでは、MCM は次を試みます。

- 必要なら死亡した一時フォームや死体をワールドに残す
- 人間のプレイヤーエンティティを復元
- authority と操作権を返す
- インベントリを保持
- 必要なプレイヤー状態を復元

これは復旧ロジックであって絶対的な不死ではありません。第三者の kill script、互換性のない engine 状態、プロセスクラッシュは対応 handoff を回避する可能性があります。

# 憑依

憑依はカタログからフォームを選ぶ代わりに、すでにワールドに存在するクリーチャーを操作します。

デフォルト入力は **G** です。

対象クリーチャーにカーソルを合わせ、憑依操作を使います。MCM は対象を確認し、互換変身を準備し、新しいプレイヤー制御状態が確定してから元のワールドエンティティを削除または retirement します。

切り替えに失敗した場合、元クリーチャーが単に消えることは避けます。

憑依は MCM 内蔵カタログだけに限定されません。他 Mod の互換クリーチャーでも動作する可能性がありますが、すべての第三者エンティティとの互換性は保証されません。

# Player 項目

**PLAYER** はクリーチャーカタログの特殊項目で、通常の polymorph 対象ではありません。

Spawn 操作では別個のプレイヤー風キャラクターを作成し、適切な見た目と最大 HP 情報のコピーを試みます。

すでに人間のプレイヤーに **PLAYER** の変身操作を使っても複製にはなりません。現在別フォームなら、人間へ戻る操作として使われます。

# シングルプレイ Game Over 復旧

Standalone のシングルプレイビルドには、Noita 標準 Game Over 画面向けの追加復旧経路があります。

ネイティブ連携が必要なゲーム構造を安全に識別できた場合、MCM は Game Over UI に **「I didn't die」** アクションを追加します。

プレイ中、MCM はプレイヤー状態のローリングバックアップを維持します。復旧ボタンは UI クリック内で直接すべてを再構築せず、MCM の通常更新経路へ復旧要求を送ります。

対応復旧では次を試みます。

- 生存プレイヤーエンティティを復元または取得
- そのエンティティを再び authoritative にする
- engine の Game Over 状態を解除
- 操作権と利用可能なプレイヤー状態を戻す
- Game Over の音声、音楽、UI 状態を可能な範囲でクリーンアップ
- 復旧直後に短い保護時間を与える

ネイティブ helper は fail-closed 設計です。固定アドレスへ永続的に書き込むのではなく、実行中の対応 Noita executable 内で既知構造を探索します。ゲーム更新後に期待構造を安全に識別できない場合は、不明な場所へ書き込まず任意復旧機能を使用しません。

# 天候と時間

MCM は現在の実装で公開されるプリセットや個別パラメータを含む、対応天候・時間状態を制御できます。

強制状態はあとからゲーム本来の制御へ解放できます。たとえば特定時刻を固定したあと、その設定を MCM 管理から外し、Noita の自然な時間進行へ戻せます。

天候変更は一方向のコンソールコマンドではなく、管理される状態として扱われます。

# ワールドルール

**RULES** セクションは対応するグローバルなゲーム挙動を変更します。

対象例:

- クリーチャー間関係
- ゴールドの挙動
- 呪文使用
- fog of war
- 一部キル報酬
- 回復ドロップ
- 血液関連挙動
- 重力
- 物理挙動
- キック力
- 物理ジョイント
- 昼夜サイクル
- その他の対応グローバル設定

重要な設計目標は可逆性です。

対応ルールでは元状態を保存または導出し、あとで戻せるようにします。倍率系は変更済み値へ繰り返し掛けるのではなく、元の値に対して適用します。

多数のエンティティや物理オブジェクトに触れるルールは、メニュークリック 1 回で世界全体を同期的に書き換えず、上限付き処理を複数フレームに分散します。

# テレポート

テレポートセクションには、メインルート、Holy Mountains、主要なサイドエリア、その他対応地点など、ワールド内の準備済み目的地があります。

プレイヤーを動かす前に、MCM は目的地周辺の読み込みを要求し、固体地形の中へ直接置く代わりに近くの利用可能な空間を探します。

テレポートは、ワールド側が実際に読み込みと有効地点提供を行えることに依存します。大きく改変されたワールドでは fallback が必要な場合があります。

# Entangled Worlds

**Entangled Worlds / Noita Proxy は任意です。** EW がなくても MCM は動作します。

EW がある場合、MCM は追加の multiplayer-aware 挙動を有効化します。MCM 独自の同期状態を利用する場合、すべての peer で互換性のある MCM ビルドを使うことを推奨します。

## Authority とフォーム

変身プレイヤーが意図せず第 2 のネットワーク authority を残さないよう、プレイヤーフォームには特別な ownership 処理が必要です。

対応範囲で MCM は EW とフォーム ownership、retirement、人間への復帰を調整します。Boss や Kolmi 系エンティティには、authority 重複や古いネットワーク制御コピーを防ぐための追加 lifecycle 処理があります。

MCM-owned フォーム状態と判断されないエンティティでは、通常の EW 死亡処理が引き続き担当します。

## アイテム、杖、呪文

可能な限り、MCM は独自の平行転送システムではなく EW 標準の item / inventory 機構を利用します。

確定した杖や呪文インベントリ変更では、連携が利用可能なら適切な multiplayer refresh を要求します。MCM が作成したワールドアイテムは EW 標準 world-item 経路へ渡せます。

## パーク

通常のパーク pickup は EW 標準 world-item 同期を利用できます。MCM のパーク状態処理は refresh と上限付き操作を調整し、大量処理でコピーごとに高コストのグローバル更新を出さないようにします。

## 素材

素材ペイントはワールドセル変更であり通常アイテムではないため、専用互換経路があります。

MCM はペイント処理量を制限し、chunk 境界で作業を分割し、同期変換処理を出す前に EW に必要な world-frame / persistence 手順を調整します。まだ読み込まれていない streaming-edge chunk は、現在のストローク全体を止めず後回しにされます。

狙いは、近くの EW peer が MCM の通常 UI 操作を filename-only PixelScene 呼び出しとして遠隔再生しなくても、対応している描画済みワールド状態を見られることです。

ただし EW の material id 前提はそのままです。受信側に存在しない素材や、engine の素材レジストリが互換でない素材を正しく生成することはできません。

## 天候、憑依、ワールド状態

対応する MCM multiplayer 状態には、天候、憑依、一部ワールドルール / lifecycle 挙動の調整も含まれます。Authority チェックにより、2 つの peer が同じ状態を同時に所有しようとすることを避けます。

EW 対応は意図的に保守的です。安全な同期経路を証明できない場合、すべてのシングルプレイ操作が multiplayer-safe であるかのように振る舞わず、正しいローカル動作を優先します。

# 互換性と制限

Noita の多くのシステムは、疎結合なエンティティ、XML、Lua コンポーネント、ネイティブ engine 挙動で構成されています。そのため MCM はすべての改造エンティティや将来のゲーム更新との完全互換を保証できません。

主な制限:

- Spawn できるクリーチャーが安全なプレイヤーフォームとは限らない
- パークを付与できても信頼できる逆操作があるとは限らない
- 外部への呪文 / アイテム handoff は内部 snapshot から常に Undo できるとは限らない
- 第三者スクリプトは対応している死亡・復旧経路を回避する場合がある
- ネイティブ復旧は対応 Noita executable の挙動に依存し、必要構造が識別できなければ fail-closed する
- Entangled Worlds は受信側レジストリにない素材を同期できない
- 大きく変更されたインベントリ、エンティティ、ワールドルールは Mod 固有の互換対応が必要な場合がある

MCM は元状態の保持と失敗した変更の rollback を重視しますが、リアルタイムのゲーム状態を書き換えるサンドボックスツールが、あらゆる第三者 Mod 組み合わせを完全トランザクション化することはできません。

# 保存データ

MCM はセッションをまたいで保持すべきユーザー状態を保存します。対応設定、キー割り当て、メニューレイアウト、杖プリセットなどが含まれます。

Mod ID は安定しているため、通常更新では対応保存データを引き継げます。ただし新しい standalone ビルド導入時は Mod フォルダ全体の置き換えを推奨します。新旧ファイルを混在させると古い runtime ファイルが残る場合があります。

# トラブルシューティング

## Mod が表示されない

パスの末尾が次になっているか確認してください。

`mods/metamorph_creative_menu/mod.xml`

`metamorph_creative_menu` より上に余分なアーカイブフォルダがあると、Noita は Mod を正しく認識できません。

## ネイティブ機能や素材機能が動かない

**Unsafe Mods** が許可され、Workshop ファイルと混在していない GitHub standalone ビルドを導入しているか確認してください。

## メニューを開くとゲーム側操作も発動する

カスタムキー割り当ての競合を確認してください。MCM は重複を表示しますが、意図して使う場合は保持できます。

## クリーチャーへ安全に変身できない

Spawn 可能な XML エンティティすべてがプレイヤーフォーム対応ではありません。特別対応が必要なクリーチャーには正確なパスベースのルールがあります。

## パークを削除できない

削除は、追跡状態に対して MCM が対応逆操作を持つ場合のみ提供されます。これは意図的です。推測によるクリーンアップは無関係なプレイヤー状態を壊す可能性があります。

## Multiplayer で peer ごとに挙動が違う

全参加者で互換 MCM ビルドを使い、Noita / Entangled Worlds 環境も互換にしてください。MCM は不一致な素材レジストリや、他 Mod による任意のネットワーク変更を修復できません。

# バグ報告

有用な報告には次を含めてください。

- 何をしようとしていたか
- MCM の正確なセクションと操作
- 問題が single-player、Entangled Worlds、または両方で起きるか
- standalone / Workshop のどちらを使っているか
- 他の gameplay Mod が有効か
- 安定した再現手順
- 可能であれば関連 Noita / EW ログ

変身、憑依、アイテム、素材の問題では、可能なら正確なエンティティや素材を示してください。翻訳表示名より技術 ID の方が有用な場合が多いです。

# リポジトリと開発ソース

このリポジトリは、プレイヤーがダウンロードする削減済みアーカイブではなく、**完全な開発ツリー**を意図的に保持します。

`metamorph_creative_menu/` には runtime コードに加えて次が含まれます。

- 自動テスト
- QA ツール
- 診断
- ネイティブソース
- ビルドツール
- release cleanup ルール
- 開発ドキュメント

これらは開発と回帰テストに必要なので GitHub source に残ります。インストール用 player ZIP は別に生成され、development-only 内容を除外します。

Player パッケージには release 専用クリーンアップも適用され、最小限の player `README.txt` が生成されます。一方 source tree では開発ドキュメントを保持します。

# テスト

自動テストは `metamorph_creative_menu/tests/` にあり、Python の contract check と Lua mock test を組み合わせています。

Release workflow はリポジトリルートから完全な imported source に対してテストを実行し、合格後に player build を公開します。Lua mock 部分には `texlua` が必要です。

Source hygiene チェックは production-facing なファイルとドキュメントについて、開発履歴の残骸、古い debug surface、偶発的なプロセス生成物の混入も防ぎます。

# Source アーカイブの import と release 流程

完全な開発 source は `Metamorph-Creative-Menu-v...zip` 系のアーカイブから import できます。

Import workflow はアーカイブ構造を確認し、完全な開発コンポーネントを要求し、source hygiene と回帰テストを実行してから imported tree を commit します。

ModWorkshop / player-style アーカイブは開発 source として扱われません。

公開 `latest-build` release は、その完全 source から別の player-builder で生成されます。Builder は QA、テスト、診断、ネイティブソース、その他 development-only payload を削除し、release cleanup ルールを適用し、最終アーカイブを検証してから安定 download asset を更新します。

この分離により、リポジトリは開発に必要な完全性を保ちながら、通常のプレイヤーダウンロードは小さく、開発用 instrumentation を含まない状態にできます。
